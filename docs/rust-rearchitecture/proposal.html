Executive summary

This proposal re-architects the FAA Aeronautical Product Release API (APRA) from a Java 1.8 monolithic Jersey WAR into a modern Rust-based platform. Rust is a strong fit for APRAs performance-sensitive URL construction, content negotiation, and network I/O workload. It offers memory safety without a garbage collector, predictable performance under concurrency, and a minimal runtime footprint that simplifies FISMA/STIG hardening and reduces container attack surface.

Compared to the current stack, the Rust solution reduces latency, memory use, and startup time while improving reliability and security. By adopting Axum (or Actix Web) on the Tokio async runtime, and standardizing on Serde for JSON and quick-xml for XML, APRA can preserve existing API semantics, including XML/JSON outputs, editions (CURRENT, NEXT, CHANGESET), and URL validation via HTTP HEAD, while incrementally decomposing long-lived services into independent microservices behind an API gateway.

Current state analysis

Overview

APRA runs as a servlet-based Java 1.8 WAR using Jersey 2.25.1. It exposes approximately twelve service areas spanning IFR/VFR and data products, with XML/JSON response formats, edition handling (CURRENT, NEXT, CHANGESET), and optional URL HEAD checks. Swagger 1.5.0 documents the API. The Maven build references legacy dependencies including Log4j 1.2.12, with an internal apraresponse JAXB model and external FAA repositories (aeronav, tod) plus Denodo-backed metadata.

Key files verified in repository:
  • pom.xml (Java 1.8; Jersey 2.25.1; Log4j 1.2.12; swagger-jersey2-jaxrs 1.5.0; apraresponse; MOXy)
  • src/main/java/gov/faa/ait/apra/api/BaseService.java (edition/format validation, URL verification)
  • src/main/java/gov/faa/ait/apra/api/SectionalCharts.java (table-driven service)
  • src/main/java/gov/faa/ait/apra/cycle/ChartCycleClient.java (28/56-day cycle logic via Denodo endpoint)
  • src/main/java/gov/faa/ait/apra/api/DownloadServiceApp.java (JAX-RS application + Swagger)
Operational characteristics

The monolith centralizes cross-cutting concerns in BaseService, enabling common validation and HEAD checks. City-based VFR products are table/Denodo-driven; cycle-based IFR/CIFP/NASR rely on the cycle client. URL construction logic is embedded per service and controlled by bootstrap Config flags. Logging uses SLF4J/Log4j with request correlation via ProductApiListener.

Risks include legacy libraries (Log4j 1.x), JVM startup and memory overhead for a primarily network-bound workload, WAR/servlet container management, and slow dependency patch cycles. XML handling via JAXB/MOXy remains functional but increases memory use under load. The deployment model lacks modern container hardening defaults.

Proposed Rust architecture

Framework and runtime

Web framework

Recommend Axum (tower-based, ergonomic, widely adopted) with Tokio async runtime. Alternative is Actix Web for maximum throughput; both meet APRA needs. Axums ecosystem with tower layers, tracing, utoipa for OpenAPI, and hyper provides a clean path for structured middleware and observability.

Serialization

Use Serde for JSON, and quick-xml with serde integration for XML parity with current JAXB models. Define canonical response types (ProductSet, Edition, Product) to preserve schema. Support content negotiation via Accept header to return JSON or XML.

API documentation

Adopt utoipa (OpenAPI generator) with Axum, producing Swagger UI in non-production and static OpenAPI JSON for publishing. Maintain contract compatibility with existing endpoints and parameters, including edition and format handling.

Logging and telemetry

Use tracing with tracing-subscriber for structured logs and request correlation (trace IDs), optional opentelemetry export. Enforce STIG security headers in a middleware layer. Emit JSON audit logs for access events.

Service decomposition strategy

Decompose the monolith along existing functional seams while keeping a stable API through a gateway. Start with the highest-traffic and lowest-coupling services:

  1. Cycle Service: encapsulates 28/56-day cycle retrieval and caching; provides edition resolution for dependent services.
  2. IFR Enroute Service: URL builders for low/high/area and oceanic charts.
  3. VFR Sectional/TAC/Helicopter Service: table-driven lookups; internal adapter for Denodo or replacement metadata source.
  4. CIFP & NASR Service: 28-day cadence products.
  5. DDOF Service: daily obstacle files with change-set support.
  6. Compatibility Gateway: preserves current URLs and content negotiation, orchestrates to Rust services during migration.

Each service is an independent Rust crate with a shared apra-model crate for response types and shared apra-config for settings and feature flags (e.g., HEAD check toggle). Shared apra-security crate exposes STIG-compliant headers and audit logging helpers.

Data and URL construction

Preserve existing URL patterns, including FAA host paths and file naming conventions. Implement a UrlBuilder abstraction per product family with edition-aware templates. Support optional URL verification via async HEAD requests with configurable timeouts and proxy support, mapped from existing Config flags. Table-driven products read metadata via a repository interface that can target Denodo or a cached store.

Introduce a lightweight cache (in-memory with optional Redis) for cycle data and frequently requested geoname maps to minimize Denodo traffic and improve tail latency. Caches use bounded TTL (e.g., 212 hours for cycle, 24 hours for city tables) with proactive refresh.

Containerization and deployment

Containers

Produce static MUSL binaries with x86_64-unknown-linux-musl, then package into a distroless or scratch image. Resulting image sizes are typically under 30MB, with near-instant startup. Supply non-root user, read-only rootfs, and seccomp/apparmor profiles.

Orchestration

Deploy to Kubernetes or ECS behind an API Gateway. Use a shared gateway route table to maintain legacy paths and route to Rust services. Apply HPA on CPU/utilization and p95 latency. Blue/green or canary deployments via progressive delivery.

Security

STIG/NIST hardening: TLS 1.2+, strict headers, no shell in container, file system read-only, minimal capabilities. Inject configuration via environment variables or sealed secrets. Centralize audit logging and metrics to SIEM/observability backends.

Build & CI

Use Cargo workspaces for multi-crate builds, GitHub Actions for CI, Trivy/Grype for image scanning, cargo-deny for dependency vetting, and cargo-audit for advisories.

Rust-specific considerations

Memory safety and performance

Rusts ownership model eliminates entire classes of memory errors (use-after-free, data races) without a GC. This is well-suited to APRAs I/O-bound workflows and frequent string manipulation for URL building. Static binaries and low baseline memory usage reduce cold start and steady-state costs.

Async/await and backpressure

Axum on Tokio provides structured concurrency with async/await, enabling efficient HEAD checks and Denodo calls. Use connection pools with timeouts, bounded task queues, and tower limits to provide backpressure and prevent overload under surge traffic.

Error handling

Adopt thiserror for domain errors and map to HTTP responses with consistent JSON/XML error envelopes mirroring BaseService messages. Use anyhow at boundaries where necessary, but prefer typed errors in service code.

Dependency management and testing

Use Cargo workspaces and lockfiles for deterministic builds. Apply cargo-audit and cargo-deny in CI. Testing includes unit tests for UrlBuilder templates, integration tests with local mock servers for aeronav/tod/Denodo, property-based tests for input validation, and load tests (k6 or bombardier). Benchmarks via criterion for hot paths.

API documentation

Use utoipa to generate OpenAPI 3 schemas from Rust types and handlers. Serve Swagger UI only in non-production. Publish versioned OpenAPI JSON to internal artifact storage for consumers.

Risk mitigation

Technical risks

Potential risks include team ramp-up on Rust idioms, XML parity with JAXB, Denodo client integration, and ensuring exact backward compatibility. Mitigations: start with Cycle Service to establish patterns; build a contract test suite from current Java outputs; use golden files for JSON/XML payloads; maintain a compatibility gateway routing legacy paths while services migrate.

Security and compliance

Apply STIG/NIST controls: whitelist validation on inputs, sanitize outputs, strict TLS, STS and CSP headers, JSON audit logs for authentication/authorization/data access, generic error messages, no secrets in images, environment-based configuration. Use distroless/scratch images with read-only FS and a non-root UID.

Team enablement

Provide Rust workshops, pair programming on initial services, and code templates with examples. Add lint rules (clippy) and enforce CI checks to standardize idioms. Document patterns for XML models and content negotiation.
